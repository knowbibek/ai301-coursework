# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Issue-specific claim | Claim comment read against the issue title, body, and thread | Names the actual symptom, affected behavior, or concrete investigation for this issue. A generic request to be assigned, copied boilerplate, or a claim about a different bug fails. | required |
| Environment traceable | Repro report's environment record compared with the issue's target and repo facts | Identifies the OS, relevant runtime/library/tool versions, and code state sufficiently to locate the attempted setup. Any version or configuration difference that affects the issue is explicit; an incompatible setup cannot prove the target bug. A precise release, commit, or otherwise identifiable code state suffices; do not demand irrelevant hardware or every transitive dependency. | required |
| Steps rerunnable | Repro report's setup, commands, inputs, fixture contents, and trigger | A stranger can reconstruct the reported attempt from the stated starting state through the trigger without guessing a critical command, input, setting, or inaccessible local artifact. Standard documented setup may be referenced precisely. Judge whether the sequence can be followed, not its length or headings. | required |
| Evidence addresses target | Repro report's actual output, logs, screenshots or other artifacts read against the issue's symptom, target path, and preconditions | Supplied artifacts show the reported result for the issue's actual trigger and relevant code path. A claim of reproduction needs the target behavior, not merely another exception, a setup failure, an unrelated test, or a screenshot of a different state. A cannot-reproduce report passes when artifacts show a meaningful attempt of the target steps and the observed non-failing result. Claims without observable artifacts fail. | required |
| Honest outcome | Repro report's conclusion compared with its steps and artifacts; claim's promises | States what was actually observed, distinguishes expected from actual behavior, and limits conclusions to what the attempt establishes. An evidenced cannot-reproduce or environment-limited result is acceptable when the target was meaningfully attempted and limitations are explicit. Do not call an adjacent failure a reproduction or imply tests/fixes were completed without proof; do not promise a fix or deadline in the claim. | required |
| Repository conventions | Repo-facts template and contribution/AI policy compared with both candidate comments | Meets the repository's explicit applicable reporting requirements, including AI-use disclosure when required. Judge required information wherever it appears, not exact heading names unless the repo mandates a format. Silence about AI policy does not create a disclosure requirement; an explicit prohibition must be respected. | required |
| Standalone respectful communication | Claim and repro comment wording, issue thread, and repo-specific house rules | Comments contain the author's own concrete investigation and evidence, use a respectful tone, and can stand alone. Unsupported blame, demands, piggyback confirmation, and boilerplate in place of substantive information fail. In Path Review, another student's claim is not a blocker. Terse complete writing passes. | required |

## Verdict rule

Accept only if every applicable required check passes. A fail or unclear on any applicable required check means reject; preferred checks never change the verdict. In claim-only live mode, grade claim and repo-convention evidence, but mark report-dependent checks unclear with evidence "not yet applicable: claim-only draft" and exclude them from the verdict. In full-package live mode and all eval runs, apply every check. An honest cannot-reproduce is eligible for accept; honesty alone cannot compensate for missing steps, an incompatible target, or absent artifacts.
